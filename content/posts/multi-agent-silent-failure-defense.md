# 多 Agent 协同中的静默错误防范机制

> [!IMPORTANT]
> **本文探讨的核心问题：**
> 1. 在多 Agent 系统中，上游 Agent A 输出了一个“看似合理但语义错误”的结果（例如由于幻觉产生的数据），下游 Agent B 会如何处理？
> 2. 整个系统应该如何设计，以避免这种逻辑错误在执行链条中“静默传播（Silent Error Propagation）”并被级联放大？

在多 Agent 协同系统（如 AutoGen、CrewAI 或自定义多 Agent 链）中，Agent 之间通常采用自然语言或松散的 JSON 进行信息传递。

这种松耦合设计带来了极高的灵活性，但也埋下了一个致命的安全隐患：**级联错误传播**。一旦上游 Agent A 编造了一个谎言，下游 Agent B 通常会全盘接受，并基于这个谎言编造更大的错误，最终导致整个系统静默崩溃，输出毫无价值的垃圾数据。

---

## 一、 下游 Agent B 会如何处理错误输入？

如果没有任何工程防护，当下游 Agent B 接收到上游 A 的“伪造但流畅”的文本时，它会表现出以下行为：

1.  **无条件顺从与迎合（Yes-Man Effect）**：
    大模型在训练中被对齐得非常温顺。B 看到上下文里 A 给的数据，会天然地认为“这是已经发生的客观事实”，它会顺理成章地在这个事实基础上继续往下写，根本不会怀疑其真实性。
2.  **幻觉级联放大**：
    比如 Agent A 负责查询公司员工，因幻觉输出：“张三是销售部经理”（实际上张三是研发部员工）。
    Agent B 负责算奖金，收到 A 的输入后，会调用销售部的奖金系数（例如 1.5），算出张三的年终奖是 15 万。
    **结果**：错误在传递中被固化并包装成了合法的财务数据，财务主管最终收到的报表看上去毫无破绽，其实数据完全是错的。
3.  **静默失败**：
    由于整个链路没有抛出任何系统级报错（Python 没有 Crash，API 也没有 500），系统会“静默”地完成所有步骤，开发者完全无法在监控中察觉到异常。

---

## 二、 避免静默传播的四大工程屏障

为了防止错误在多 Agent 链条中暗度陈仓，我们必须在 Agent 之间建立“信任边界”与“校验机制”。

```
[Agent A] 
    │
    ▼ (输出伪造数据)
┌──────────────────────────────────────────┐
│ 1. 强契约校验层 (Pydantic / JSON Schema)    │ --> 阻断非法格式/范围
└──────────────────────────────────────────┘
    │
    ▼ (通过结构校验)
┌──────────────────────────────────────────┐
│ 2. 环境一致性断言层 (Watchdog Guard)       │ --> 阻断与物理数据库/现实冲突的数据
└──────────────────────────────────────────┘
    │
    ▼ (通过物理断言)
┌──────────────────────────────────────────┐
│ 3. 下游主动质询机制 (Critic & Challenge)    │ --> B 审视逻辑：“这合理吗？”不合理退回
└──────────────────────────────────────────┘
    │
    ▼ (安全采纳)
[Agent B]
```

### 1. 强契约数据通信（Structured Data Contracts）

**大白话比喻**：不要让 Agent A 和 B 用“大白话”交接工作。必须用“表格”交接，每个表格的格子里填什么，都有严格的类型和范围规定。

*   **工程实现**：
    *   严禁 Agent 之间传递自由文本。必须使用 **Pydantic** 或 **JSON Schema** 定义它们之间的通信协议。
    *   在 Agent A 输出后，宿主程序必须执行一次硬校验（`schema.validate(output)`）。如果 A 输出的“年龄”是 `-1` 或“部门”不在预设的 `['销售', '研发']` 列表中，**立即在拦截层报错**，直接打回给 A 并附带报错信息，强迫 A 重新生成。

---

### 2. 环境一致性断言（Environmental Assertions / Watchdog）

**大白话比喻**：在 A 和 B 的传球通道中间，站着一个“手持规矩的裁判”。裁判不听大模型的解释，只看数据库里的真实记录。

*   **工程实现**：
    *   在应用层编写一个独立的 **Watchdog（看门狗）** 模块。
    *   当 A 产生输出后，Watchdog 会用确定性代码（Deterministic Code）去后端数据库或第三方 API 进行真伪校验（Grounding Test）。
    *   例如：A 输出“张三是销售部经理”。Watchdog 捕获后，立刻运行一条 SQL：`SELECT department FROM employees WHERE name='张三'`。
    *   如果 SQL 返回的结果是“研发部”，Watchdog 立刻熔断传输，不让该信息流向 B，同时触发报错：“数据不一致：张三属于研发部，而非销售部，请重新核对。”

---

### 3. 双端握手与主动质询机制（Active Challenge & Critic）

**大白话比喻**：下游 Agent B 不是一个盲目听话的实习生，而是一个经验丰富的“审计员”。收到 A 的报告后，B 会先反问：“你给的这个数对不对？你从哪儿看出来的？”

*   **工程实现**：
    *   在 Agent B 的工作流最开始，引入一个“质询（Challenge）”环节。
    *   Prompt 设计：“你收到了上游提供的信息 X。请根据你的专业常识以及已知上下文，评估该信息是否存在逻辑漏洞、前后矛盾或明显幻觉？如果存在，请输出 `CHALLENGE: 你的理由`；如果完全合理，请输出 `ACCEPT`。”
    *   一旦 B 触发了 `CHALLENGE`，宿主程序就会把对话挂起，将 B 的质疑反馈给 A，让 A 进行自我修正（Self-Correction）并重新输出。

---

### 4. 链路回退与重新规划（Backtracking & Re-planning）

**大白话比喻**：如果走到第 5 步才发现第 2 步干错了，应该允许系统“时光倒流”，退回到第 2 步重做，而不是让整个工厂流水线直接报废。

*   **工程实现**：
    *   在多 Agent 系统中引入一个顶层协调器（Orchestrator）。
    *   每个 Agent 的输出和状态都会被版本化保存（State Snapshots）。
    *   当下游 B 发现致命语义错误时，可以向 Orchestrator 发送一个带有错误根源定位的 `Rollback` 信号。
    *   Orchestrator 接收后，自动将系统状态回滚到 Step 2，将 B 的报错信息作为 `User Instruction` 输入给 A，让 A 在正确的上下文引导下重新工作。

## 三、 四种防范手段的对比

| 防范策略 | 实现复杂度 | 性能开销 | 核心拦截点 | 推荐指数 |
| :--- | :--- | :--- | :--- | :--- |
| **1. 强契约数据校验** | 低 | 极低（纯代码计算） | 格式、类型、值范围异常 | ⭐⭐⭐⭐⭐ (必须使用) |
| **2. 环境一致性断言** | 中等 | 低（SQL / 查 API） | 与客观数据库/事实冲突 | ⭐⭐⭐⭐⭐ (读写业务必备) |
| **3. 下游主动质询** | 高 | 高（多消耗一次 LLM 调用） | 逻辑矛盾、语义幻觉 | ⭐⭐⭐ (复杂推理业务推荐) |
| **4. 链路回退重划** | 极高 | 中等（回滚重算） | 灾难性错误后的系统自愈 | ⭐⭐⭐ (大型长链路 Agent 系统) |

---

## 四、 总结一句话

防范多 Agent 错误静默传播的核心在于：**把下游 Agent 当成“有审判权的审计员”，而不是“盲从的执行者”；在 Agent 传递数据的管道上布置“强契约校验”和“数据库断言”的铁闸门，宁可报错熔断，绝不放行脏数据。**

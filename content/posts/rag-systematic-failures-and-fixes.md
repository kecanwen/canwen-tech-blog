# RAG 系统性失败场景与工程补救方案

> [!IMPORTANT]
> **本文探讨的核心问题：**
> 1. 为什么 RAG 依赖向量相似度检索时，“语义相似”不等同于“答案正确”？
> 2. RAG 会在哪些典型场景下遭遇“系统性失败”（检索召回阶段就彻底出错）？
> 3. 针对这些天生缺陷，工业界有哪些成熟的工程补救手段？

RAG（检索增强生成）被广泛用于解决大模型的“幻觉”和知识时效性问题。然而，RAG 的底层支柱——**向量相似度检索（Cosine Similarity）**，本质上是一种概率近似。

在数学上，`Vector("猫不能吃巧克力")` 和 `Vector("猫可以吃巧克力")` 在高维向量空间中的距离可能极近，因为它们共享了几乎所有的主题词（猫、吃、巧克力）。

这种“只认主题，不分逻辑”的数学特性，导致 RAG 在特定业务场景下会遭遇灾难性的**系统性失败**。以下是两种最典型的失败场景及工程解法。

---

## 场景一：时间与状态漂移（时效逻辑的失效）

### 1. 为什么会系统性失败？
*   **现象**：用户询问：“Kevin 现在的工资是多少？”
*   **知识库数据**：
    *   切片 A：“2023年，Kevin 升职，现在的工资是 10k。”
    *   切片 B：“2026年，Kevin 再次升职，现在的工资是 25k。”
*   **失败根源**：从语义相似度来看，切片 A 和切片 B 都高度匹配“Kevin”和“工资”的主题。向量数据库在计算距离时，无法理解“2026年”比“2023年”更新、更正确。它可能会因为切片 A 的字面匹配度更高（或者干脆由于随机哈希分布），把切片 A 优先排在 `Top-1` 喂给 LLM。
*   **结果**：LLM 极其自信地回答了错误的旧数据（10k），导致严重的业务错误。
*   **大白话比喻**：你想去报刊亭买“今天的最新报纸”，老板因为“语义相似”，给了你一份十年前的报纸，因为上面也写着“今日新闻”。

### 2. 工程补救手段

#### ① 元数据过滤（Metadata Filtering）与硬时间窗限制
在文档灌入（Ingestion）阶段，强制提取文档的“创作时间”或“状态版本”，并作为结构化字段（Metadata）写入向量数据库。
*   在用户查询时，利用小模型（或规则）解析出时间意图（如“现在”、“最近”），在执行向量检索时加上硬性条件限制，例如：`metadata.year >= 2026` 或直接过滤旧版本标签。

#### ② 时间衰减重排（Time-Decay Re-ranking）
在向量相似度得分的基础上，乘上一个时间衰减系数（Time-Decay Factor）：
$$\text{Final Score} = \text{Vector Score} \times e^{-\lambda (t_{\text{now}} - t_{\text{doc}})}$$
这样可以确保在语义相近的情况下，越新的文档得分越高，从而优先排在前面。

## 场景二：全局概括与多文档信息聚合的“管中窥豹”

### 1. 为什么会系统性失败？
*   **现象**：用户提问：“过去一年中，我们公司在 AI 领域的研究方向经历了哪些阶段性的战略变化？”
*   **知识库数据**：散落在几百个不同项目的周报、季度总结文档中。
*   **失败根源**：向量检索的本质是“针寻草芥（Needle in a Haystack）”，它适合定位具体的、局部的细节（比如某一周做了什么）。但当面对“总结战略变化”这种需要**鸟瞰全局、多文档归纳**的问题时，向量检索只捞取 `Top-K`（例如前5个切片）。这 5 个切片可能只涵盖了 3 月份和 8 月份的零碎记录，完全遗漏了其他月份。
*   **结果**：LLM 只能根据这几个片面的切片拼凑出一个非常局限、甚至完全错误的“战略变化”总结。
*   **大白话比喻**：你问“红楼梦讲了个什么故事？”，向量检索帮你找到了书中描写“吃螃蟹”、“作诗”的 3 个段落，你试图只通过这 3 个段落概括整本书。

### 2. 工程补救手段

#### ① GraphRAG（知识图谱增强检索）
微软开源并推广的架构。它在向量之外，引入了**实体与关系图谱**。
1.  **离线阶段**：LLM 扫描全库，提取出实体（如“大模型项目”、“AI 战略”）和它们之间的关系，并生成各个层级的“社区摘要（Community Summary）”。
2.  **在线阶段**：当遇到全局问题时，不再检索原始切片，而是检索“社区摘要”和实体网络。这使得模型可以直接在“大纲级别”进行总结，避免漏掉关键节点。

#### ② 层次化切片与摘要树（Parent-Child / Summary Chunking）
不要只做单一维度的粗暴切片。
*   **结构设计**：对每篇长文档生成“文档摘要”和“章节摘要”，并作为 **Parent Chunk**；将具体段落作为 **Child Chunk**。
*   **检索策略**：
    *   如果是具体问题，检索 Child Chunk，并返回 Parent 的上下文。
    *   如果是宏观概括问题，**只检索 Parent Chunk（摘要层）**。这样可以在 Top-K 限制内，装下跨度极广的全局信息。

## 场景三：否定极性与微小边界条件混淆（差之毫厘，谬以千里）

### 1. 为什么会系统性失败？
*   **现象**：用户询问：“我能吃感冒药 A 吗？我目前正在服用降压药 B。”
*   **知识库数据**：
    *   切片 A：“服用降压药 B 的患者，**绝对不可**联合服用感冒药 A，会导致严重副作用。”
    *   切片 B：“服用降压药 B 的患者，可以服用感冒药 C，注意休息。”
*   **失败根源**：对于 Embedding 编码器来说，切片 A 中包含了几乎所有 Query 的关键词，且“降压药 B”和“感冒药 A”的同时出现让其语义距离极近。然而，向量模型对“绝对不可”、“不能”等否定词（Negation）和逻辑极性很不敏感，极易把切片 A 当作最相关的资料召回。如果 LLM 在生成时漏看了“绝对不可”这个否定修饰词（在长上下文窗口中经常发生注意力涣散），就可能给出致命的“可以服用”的错误回答。
*   **大白话比喻**：你问“这里有毒吗？”，检索系统给你推荐了“这里有毒，请勿靠近”和“这里无毒”，但因为它们都讨论了“毒性”，系统把“有毒”放在了第一位，并把“请勿靠近”给截断了。

### 2. 工程补救手段

#### ① 引入交叉编码器重排（Cross-Encoder Re-ranker）
*   **原理**：向量检索（Bi-Encoder）是把 Query 和 Doc 分开编码成向量再算内积，丢失了大量局部关联细节。
*   **解法**：在向量检索出 Top-40 后，引入一个 Cross-Encoder（重排模型，如 Cohere Rerank 或 BGE-Rerank）。它将 `[Query, Document]` 拼接在一起作为一个整体输入大模型计算注意力（Attention）。Cross-Encoder 能够以极高的精度识别出“不能”、“禁止”、“但是”等极性词与实体之间的强关联，重新对文档打分，把真正安全正确的切片排在最前面。

#### ② 意图分类与 Query 改写（Query Rewriter）
*   在检索之前，先使用微型 LLM 评估 Query 的意图极性：这是一个安全限制提问（否定意图）还是一个常规操作提问（肯定意图）。
*   如果是安全限制提问，在检索召回文档后，启动**硬规则过滤器**（比如基于正则表达式或敏感词列表，扫描切片里是否含有“禁止”、“不可”、“致命”等词），强制提升含有极性警告段落的权重。

## 总结：RAG 升级的黄金公式

只用向量检索的 RAG 只是“玩具级”的。要让 RAG 真正可用，工业界目前普遍采用的黄金公式是：

$$\text{企业级 RAG} = (\text{混合检索} \text{ [向量 + BM25]} + \text{元数据过滤}) \rightarrow \text{Cross-Encoder 重排} \rightarrow \text{层次化摘要/知识图谱}$$

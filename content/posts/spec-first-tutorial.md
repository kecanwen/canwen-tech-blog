# spec-first 完整教程：让 AI 先读「目录说明书」再改代码

---

## 1. 一句话

**进入任何代码模块之前，先读该目录下的 `spec.md`；让 AI 从「探索式扫代码」变成「导航式改代码」。**

`spec.md` 是一份 10~30 行的目录说明书：这个目录干什么、有哪些文件、依赖谁。AI 每次动手前先读它，就能把改动范围锁定在 1~3 个文件，而不是扫半个仓库。

---

## 2. 为什么需要它

AI 写代码时最大的浪费不是「不会写」，而是**定位成本**：

1. Glob / Grep 扫出几十个文件
2. 逐个 Read，上下文被噪声占满
3. 改错文件或漏改关联文件
4. 下次同一模块再扫一遍

`spec.md` 把「模块地图」固化成**可读、可维护、可检索**的短文档，让工作流从「探索型」变成「导航型」。

实践数据（hrs-web）：约 27 份 × 10~30 行，覆盖基础设施 + 页面模块，足以把「打开源文件数」压到 1~3 个。

| 方案 | 优点 | 缺点 |
|------|------|------|
| 单文件超长 AGENTS.md | 一处查找 | Token 贵；模块一多必腐烂 |
| 只靠 Glob 探索 | 无需维护 | 每次任务都付探索税 |
| **目录级 spec.md** | 按需加载；同步成本低 | 需要纪律（commit 校验） |

---

## 3. 先立几条原则

### 原则 1：先读后改

进入模块前必须读对应 `spec.md`。禁止：未读 spec 就目录级盲扫、一口气打开 10+ 源文件。

### 原则 2：短而全

只写：

- 一句话职责
- 文件/子目录清单 + 职责
- 依赖 / 相关路径

**不贴大段代码。** 一份控制在 10~30 行，过长就失去「扫一眼定位」的价值。

### 原则 3：一目录一份

`spec.md` 放在被描述目录旁：

```text
src/pages/tag-manager/spec.md
src/services/spec.md
```

父级可做总览（如 `src/pages/spec.md`），子模块各自维护细节。

### 原则 4：与代码同生共死

新增 / 删除 / 重命名文件，或模块职责变化 → **同一次 commit** 更新 spec。纯内部实现微调、清单未变 → 可不改。

### 原则 5：有则强制、无则不阻塞

| 状态 | 行为 |
|------|------|
| 目录已有 spec | **必须先读** |
| 项目尚无任何 spec | 不阻塞开发；**禁止擅自批量生成整树**，除非用户明确要求 bootstrap |
| 用户要求补齐 | 按落地流程生成 |

## 4. spec.md 长什么样

### 模板（直接套用）

```markdown
# {目录相对路径} — {一句话职责}

{可选：1~2 句补充业务边界，不要写实现细节。}

## 文件清单

| 文件/子目录 | 职责 |
|-------------|------|
| `index.ts` | … |
| `components/` | … |

## 依赖 / 相关

- `@/services/xxx` 或相对路径 `../yyy`
- 相关 spec：`../overview/spec.md`

<!--
写法约束：
- 总行数目标 10~30；上限建议 40
- 只写职责与清单，禁止大段代码 / 完整类型定义
- 增删重命名文件时同步更新本文件
- 纯内部实现微调且清单未变 → 可不改
-->
```

### 一个填好的例子

```markdown
# src/pages/order — 订单管理页

订单列表、详情与状态流转的业务页面；不包含支付回调（在 services/payment）。

## 文件清单

| 文件/子目录 | 职责 |
|-------------|------|
| `index.vue` | 订单列表页（搜索 + 表格 + 分页） |
| `detail/` | 订单详情（基础信息 + 操作按钮） |
| `components/OrderStatusTag.vue` | 订单状态标签 |
| `useOrderList.ts` | 列表查询逻辑（分页/筛选状态） |

## 依赖 / 相关

- `@/services/order` — 订单 API
- `@/store/order` — 订单状态管理
- 总览：`src/pages/spec.md`
```

写完后自己读一遍：能不能回答这三个问题——这个目录干什么？改某个功能通常动哪几个文件？依赖谁？顺带检查有没有把函数签名、伪代码塞进去。

## 5. 落地：怎么让一个仓库跑起来

### 先对齐范围

与负责人对齐：

1. **源码根**：`src/`？`apps/web/src/`？monorepo 哪几个 package？
2. **切分粒度**：按业务模块？按分层？二者结合？
3. **工具链**：Cursor rules（`.cursor/rules`）/ Claude `CLAUDE.md` / `AGENTS.md` 用哪些？
4. **是否全量生成**：首次建议「关键目录全覆盖」，不要只写 2~3 个示范就停。

### 扫结构、定索引

1. 列出一层/二层关键目录（忽略 `node_modules`、`dist`、`.git`、纯资源目录）
2. 画一张 spec 索引表（路径 → 一句话说明）
3. 标出**入口总览**（如 `src/pages/spec.md` 或 `src/modules/spec.md`）

```markdown
| spec 路径 | 说明 |
|-----------|------|
| src/pages/spec.md | 页面总览（入口） |
| src/pages/order/spec.md | 订单模块 |
| src/services/spec.md | API 层 |
```

### 批量写 spec.md

对每个目录：

1. `ls` / 读目录树，列出文件与子目录
2. 按第 4 节模板填职责（**不贴代码**）
3. 依赖写相对路径或别名（如 `@/services/order`）
4. 控制在 10~30 行；子模块多可分子表，仍保持短

### 挂上 Agent 规则

三个产物全文见第 6 节，可直接拷贝：

| 产物 | 作用 |
|------|------|
| `.cursor/rules/spec-first.mdc` | 每次对话强制「先读 spec」 |
| `AGENTS.md` / `CLAUDE.md` 索引段 | AI 导航入口 + 完整索引 |
| git 提交前检查约定 | 防止 spec 与代码脱节 |

要点：规则里写入**本仓库真实索引表**（不要留 hrs-web 的路径）；写明「无 spec 不阻塞、未授权不批量生成」；项目级索引**优先于**全局泛化规则。

### 试跑验收

选一个真实小任务（如「改列表筛选项」），观察 AI 是否：

1. 先读总览 / 模块 spec
2. 只打开 1~3 个源文件
3. 改完同步更新 spec（若文件清单变化）

失败信号：一上来 `Glob **/*`、连开 8 个无关文件、改完不提 spec。

### 团队约定（可选）

- MR 模板加一行：`[ ] 相关 spec.md 已更新或确认无需更新`
- 新人 onboarding：先读 `AGENTS.md` 索引，再读一个业务模块 spec
- 每季度体检一次（见第 8 节）

### 大概要多久

| 仓库规模 | 建议 spec 数 | 首次人力/Agent |
|----------|--------------|----------------|
| 小（<15 业务目录） | 10~20 | 半天以内 |
| 中（hrs-web 量级） | 20~40 | 一两天 |
| 大 monorepo | 按 package 分期 | 先试点一个 app，再铺开 |

## 6. 三个可直接拷贝的配套文件

### 6.1 Cursor 规则（`.cursor/rules/spec-first.mdc`）

```markdown
---
description: 优先读取与维护目录旁的 spec.md，避免盲目扫目录；提交前保持 spec 与代码一致
alwaysApply: true
---

# spec.md 优先策略

本仓库用目录级 `spec.md`（每个约 10~30 行）描述模块职责、文件清单与依赖。
**进入任何模块前，必须先读对应 spec.md**；禁止在未读 spec 的情况下逐文件盲扫。

## 工作流程

1. **定位 spec**：按任务路径找到对应 `spec.md`（见下方索引）；不确定归属时先读总览
2. **理解全貌**：用职责与文件清单确定要改的文件
3. **按需精读**：只打开 spec 点名的 1~3 个源文件
4. **同步更新**：新增/删除/重命名文件，或模块职责变化时，更新同目录 `spec.md`
5. **提交前校验**：commit 前对照 diff 检查受影响 spec 是否仍准确；不一致则同 commit 更新

## 何时启用

| 情况 | 行为 |
|------|------|
| 任务相关目录存在 `spec.md` | **必须先读** |
| 存在上级/总览 `spec.md` | 先读总览再读子模块 |
| 项目尚无任何 `spec.md` | 不阻塞开发；**不要擅自批量生成**，除非用户明确要求 |
| 用户要求补齐 / bootstrap | 按约定生成并维护索引 |

## spec.md 索引（请替换为本仓库真实列表）

### 总览 / 入口

| spec 路径 | 说明 |
|-----------|------|
| `{SRC}/pages/spec.md` | **页面/业务总览（入口必读）** |

### 基础设施

| spec 路径 | 说明 |
|-----------|------|
| `{SRC}/services/spec.md` | API / 服务层 |
| `{SRC}/store/spec.md` | 状态管理 |
| `{SRC}/router/spec.md` | 路由 |
| `{SRC}/utils/spec.md` | 工具函数 |

### 业务模块

| spec 路径 | 说明 |
|-----------|------|
| `{SRC}/pages/{module}/spec.md` | … |

## 快速定位

- 不确定业务归属 → 先读总览 spec
- 涉及 API → 读 services spec + 目标业务模块 spec
- 涉及路由 → 读 router spec
- 涉及公共组件 → 读 components spec

## 写法（10~30 行）

每个目录一份，只写职责与清单，不贴大段代码。职责变化才改；纯内部实现微调可不改。
```

### 6.2 AGENTS.md 索引段

```markdown
## spec.md 优先

本仓库用目录级 `spec.md`（每个约 10~30 行）覆盖关键模块。

**任何任务的第一步：读对应 `spec.md`，而非逐文件打开探索。**
spec 已列出模块职责、文件清单与依赖，足以定位需要改动的 1~3 个源文件。

新增 / 删除 / 重命名文件时，必须同步更新对应 `spec.md`。

### 开发流程

1. 读 spec.md 了解模块全貌
2. 按需打开 spec 点名的源文件（通常 1~3 个）
3. 改代码；涉及跨层时按 spec 中的依赖跳转
4. 同步更新 spec.md（清单或职责有变时）

### spec.md 索引

| 层 | 路径 | 说明 |
|----|------|------|
| 总览 | `{SRC}/pages/spec.md` | 业务入口必读 |
| 服务 | `{SRC}/services/spec.md` | API |
| … | … | … |

### 相关规则

| 规则 | 生效 |
|------|------|
| `spec-first.mdc` | 每次对话 — 先读 spec + 索引 |
| （可选）`git-workflow` 中的 spec 校验段 | 提交前一致性检查 |
```

### 6.3 git 提交前检查约定

```markdown
## 提交前 spec.md 一致性检查（必做）

每次 commit 之前，对照本次变更检查相关 `spec.md` 是否与代码一致；不一致则先更新 spec，再一并提交。

### 检查步骤

1. **看 diff 范围**：列出本次新增、删除、重命名的文件
2. **定位 spec**：找到受影响目录对应的 `spec.md`
3. **逐项核对**：
   - 文件清单是否与实际目录一致？
   - 新增/删除/重命名是否已反映？职责描述是否仍准确？
   - 依赖路径是否仍正确？
   - 新增业务模块时，总览 spec / `AGENTS.md` 索引是否已更新？
4. **更新 spec**：发现不一致，在同一 commit 中更新（保持 10~30 行，只写职责不贴代码）

### 常见场景

| 变更类型 | 需检查 |
|----------|--------|
| 增删改文件名 | 该目录 `spec.md` |
| 新增业务模块 | 总览 spec + 模块 `spec.md` + 索引 |
| 新增 service / 全局组件 / 路由 | 对应层 `spec.md` |

### 原则

- spec 与代码**同 commit**，不滞后
- 仅改内部实现、清单与职责未变 → 无需更新 spec
- commit message 仍按项目规范；spec 更新可并入功能 commit
```

## 7. 日常开发怎么用

### 不装任何工具也能用：把这段提醒贴在任务开头

在已落地 spec-first 的仓库中，把下面这段作为系统提醒或贴在长任务开头：

```text
本仓库已启用 spec-first。对本任务强制执行：
1. 定位并阅读相关 spec.md（不确定归属 → 先读业务总览 spec）
2. 根据清单确定改动文件，只打开 1~3 个源文件开始改
3. 禁止用目录级盲扫替代读 spec；仅在 spec 缺失或明显过时时，才有限探索并提议更新 spec
4. 若本次有新增/删除/重命名文件，或模块职责变化 → 同步更新对应 spec.md（及总览索引若需要）
5. 用户要求 commit 时：对照 diff 做 spec 一致性检查，不一致则同 commit 更新
回复保持简洁；不要复述整份 spec，只引用与任务相关的结论。
```

### 装了技能的话：直接 `/spec-first`

`/spec-first` 提供四种模式：

| 模式 | 用途 |
|------|------|
| `bootstrap` | 为当前/指定仓库建立整套 spec-first |
| `audit` | 审计覆盖率与一致性（默认先报告后修复） |
| `fill` | 只补指定目录的 spec |
| `daily` | 按 spec-first 执行当前开发任务 |

未指定模式时，直接说 `/spec-first` 并附仓库路径即可。

### 给新项目落地（推荐）

在目标仓库开 Cursor / Claude Code，执行 `/spec-first bootstrap`；或者把 `prompts/bootstrap-project.md` 全文贴进对话并附上仓库根路径。Prompt 会让 AI 先输出「spec 索引草案」给你确认，再批量写文件，全程不擅自改业务代码、不自动 commit。

## 8. 定期体检

每季度一次，或出现「腐化信号」时（见第 9 节）立即执行。把下面这段发给 Agent：

```text
请对当前仓库做一次 spec-first 审计。只读分析优先；发现必须改的过时 spec 时，
列出清单并询问是否直接修复（默认先给报告，用户说「修复」再写文件）。

审计项：
1. 覆盖率：关键业务/基础设施目录是否缺少 spec.md？有无多余（空目录、生成物）？
2. 一致性：随机或按 diff 热点检查若干 spec.md 的文件清单是否与目录实际一致
3. 篇幅：是否普遍 >40 行或粘贴了大段代码？标出 Top 违规
4. 索引：AGENTS.md / .cursor/rules/spec-first.mdc 中的索引路径是否都存在？是否有遗漏？
5. 可导航性：抽 2 个真实功能点，模拟「只读 spec」能否定位到正确文件

输出格式：
## 结论（一句话）
## 覆盖率（缺失/多余）
## 过时清单（路径 + 问题 + 建议）
## 索引问题
## 篇幅/反模式
## 建议动作（按优先级）

不要自动 commit。用户确认「按建议修复」后再改文件。
```

## 9. 反模式与边界

### 常见的反模式

| 反模式 | 正确做法 |
|--------|----------|
| spec 当源码副本（贴类型、贴实现） | 只写职责 + 清单 + 依赖 |
| 一个巨型 SPEC.md 管全仓 | 目录级短文件；总览只做索引 |
| 未授权就全仓生成 | 等用户明确要求 bootstrap / 补齐 |
| 写完从不更新 | 同 commit 同步；提交前检查 |
| 只读 spec 不读代码 | spec 导航 + 精读 1~3 个源文件 |
| 索引抄错项目（照搬 hrs-web 路径） | 按当前仓真实结构重新生成 |
| 叶子目录过度拆分（1 个工具函数也建 spec） | 优先覆盖业务模块/分层入口/公共能力 |

### 边界：什么时候不要用

| 场景 | 建议 |
|------|------|
| 一次性脚本、实验分支 | 可不建 |
| 纯静态资源、生成物目录 | 不建 |
| 外部 vendor / 锁死第三方 | 不建 |
| 极小仓库（<5 个源文件） | 一份 README 即可 |

### 腐化早期信号

- 多人反馈「看了 spec 还是找不到文件」→ 清单过时或粒度不对
- Agent 开始忽略 spec → 规则未 alwaysApply，或索引路径错误
- spec 普遍超过 80 行 → 该拆子模块或删代码粘贴

发现后优先跑一次 audit，再决定是修清单还是调切分。

## 10. 怎么验收

- [ ] 关键目录都有 `spec.md`，且 ≤ 约 40 行（理想 10~30）
- [ ] 有一份总览索引（写在 `AGENTS.md` 或项目级 spec-first 规则）
- [ ] Cursor / Claude 规则要求「先读 spec」
- [ ] git 提交流程含「spec 一致性检查」
- [ ] 新同事 / Agent 能仅凭 spec 指出「该改哪 1~3 个文件」

最小闭环：**规则强制先读 → spec 短地图 → 改代码 → 同步 spec → commit 校验**。缺任何一环都会慢慢腐化；四环齐备即可迁移到其他项目。

## 11. 常见问题

**会不会增加很多维护负担？**
不会。每份 spec 只有 10~30 行，只在文件结构变化时才改；commit 前顺手看一眼就行，由流程兜底。

**多大项目才值得建？**
业务目录超过 10 个或开始多人协作即可；极小仓库一份 README 就够了。

**和 README / AGENTS.md 什么关系？**
README 面向人、讲怎么用；AGENTS.md 面向 AI、讲全局约定；`spec.md` 是目录级模块地图，按需加载，三者互补。

**后端项目能用吗？**
可以。把 spec 映射到 `domain/`、`application/`、`infrastructure/`、`interfaces/` 分层即可。

**一定要配 Cursor / Claude 吗？**
spec-first 的核心是短文档 + 纪律；配规则和 commit 校验是为了防止腐化，让收益持续。

**spec 由谁维护？**
改代码的人顺手维护，commit 校验兜底，季度 audit 巡检；不需要专门的文档负责人。

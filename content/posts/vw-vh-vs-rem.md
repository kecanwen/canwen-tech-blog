# 为什么 vw/vh 成为主流，而 rem 渐进淘汰

从技术演进的角度来看，**`rem` 方案本质上是早期浏览器原生能力不足时的一种“过渡性黑科技”（polyfill），而 `vw/vh` 则是浏览器原生标准能力的最终归位**。

`rem` 的淘汰与 `vw/vh` 的崛起，是前端工程化、浏览器内核演进以及用户体验标准提升的必然结果。以下从 5 个核心维度为你深度剖析：

---

### 1. 历史宿命：`rem` 本质上是在“用 JS 模拟 vw”

在 2015 年左右（以手淘 `lib-flexible` 为代表的时代），移动端 Web 面临严重的分辨率碎片化问题。然而当时：
* **`vw/vh` 的致命痛点：** iOS 6/7 和 Android 4.4 以下的 WebView 对 `vw` 单位存在严重的 Bug（如计算延迟、旋转屏不更新、部分 Android 系统不支持）。
* **`rem` 的妥协解法：** 开发者发现可以用 JS 监听 `resize`，动态计算屏幕宽度并修改根节点 `html` 的 `font-size`：
  $$\text{html font-size} = \frac{\text{屏幕宽度}}{10}$$
  **本质上，这种做法就是强制把 `1rem` 规整为了 `10vw`**。

随着 Android 4.4+ 被彻底淘汰，现代所有移动端设备的 WebView（WebKit / Blink / Gecko）对 `vw/vh` 的支持率早已达到 **100%**。既然浏览器已经原生支持了视口单位，就没有必要再通过 JS 绕一个弯子去模拟它。手淘官方也在几年前就已经宣布废弃 `lib-flexible` 方案，拥抱 `vw`。

---

### 2. 致命缺陷：`rem` 难以回避的 4 大工程与体验痛点

#### ① JS 依赖与页面闪烁（FOUC / SSR 灾难）
* **`rem` 依赖 JS 计算：** 必须在 `<head>` 中内联一段 JS（阻断渲染）来计算 `html` 的 `font-size`。一旦脚本执行延迟、加载失败或被阻塞，页面就会出现**严重的样式崩塌或闪烁（FOUC）**。
* **SSR/静态导出（SSG）不友好：** 在服务端渲染（如 Next.js/Nuxt）时，服务器无法得知客户端真机屏幕宽度，无法预渲染正确的 `font-size`，会导致水合（Hydration）不匹配或闪烁。
* **`vw` 的优势：** 纯 CSS 引擎解析，没有任何运行时的 JS 开销，SSR 完美兼容。

#### ② 破坏系统“无障碍/字体放大”体验（微信/系统字体暴雷）
* 当用户在手机系统设置，或微信等 App 内将“系统字体”放大时，浏览器的默认基准字体大小会改变（如从 `16px` 变到 `24px`）。
* **`rem` 的两难抉择：** 
  * 如果 JS 计算 `rem` 时强制覆盖 `font-size`，就会破坏高龄/视力障碍用户的系统字体放大诉求，导致无障碍体验合规失败；
  * 如果不覆盖，基准字体改变会导致页面上所有基于 `rem` 的布局（不仅仅是文字，包括 Div 宽高、边距）全盘**爆框、错位、重叠**。
* **`vw` 的优势：** 布局元素的宽高（使用 `vw`）与文字大小（可单独使用 `px` / `rem` / `clamp`）实现**解耦**，不会因为用户调大字体而导致卡片容器变形爆框。

#### ③ 亚像素（Sub-pixel）计算精度与浮点数舍入误差
* `rem` 转换依赖乘法计算，例如 `1.23rem` 在某手机上计算出的结果可能是 `37.21875px`。
* 不同的渲染引擎对这种带小数点的浮点数像素处理不同（有的四舍五入，有的截断）。这会导致：
  * **1px 边框莫名消失或变粗**；
  * Flexbox / CSS Grid 布局中的元素产生 **1px 的缝隙或错位**；
  * 滚动条在某些尺寸下偶发出现。
* **`vw` 的优势：** 浏览器渲染引擎内部对视口百分比的硬件加速优化远好于上层 `rem` 算出来的浮点值。

#### ④ 作用域污染与微前端/组件库冲突
* `rem` 是**全局作用域**（依赖唯一的 `html` 根节点）。
* 在微前端架构、主子应用嵌套、或引入第三方 UI 组件库（如 Vant / AntD Mobile）时，如果第三方库基于 `1rem = 50px` 设计，而你的主应用基于 `1rem = 37.5px`，两者样式将**瞬间互相污染崩塌**。
* **`vw` 的优势：** 属于完全独立的原生单位，零全局污染。

---

### 3. 终极形态：现代 CSS 与 `vw/vh` 的组合拳

单独使用 `vw/vh` 曾经也有一个小缺陷：**在 Pad 或 PC 大屏上，元素会被无限放大，变得巨无比**。

而如今，现代 CSS 提供了强大的函数（`clamp()`、`min()`、`max()`），配合 `vw` 可以写出极度优雅的响应式布局，完全不需要 JS 介入：

```css
/* 彻底解决 Pad/大屏上元素过大的问题 */
.card {
  /* 
    最小值: 16px (手机小屏)
    首选值: 4vw (随屏幕动态等比缩放)
    最大值: 24px (Pad/PC端封顶，不再无限制变大)
  */
  padding: clamp(16px, 4vw, 24px);
  width: min(90vw, 600px); /* 视口宽度 90%，但最大不超过 600px */
}
```

此外，针对移动端 Safari/Chrome 软键盘弹起、顶部地址栏展开/收起导致 `100vh` 页面被遮挡的千古难题，现代 CSS 标准还引入了 **新一代视口单位**：
* **`dvh` (Dynamic Viewport Height)：** 动态视口高度（自动跟随地址栏收起/展开调整）。
* **`svh` (Small Viewport Height)：** 最小视口高度（地址栏展开时的可见高度）。
* **`lvh` (Large Viewport Height)：** 最大视口高度（地址栏收起时的可见高度）。

---

### 4. 总结与现代选型建议

| 维度 | `rem` 方案 | `vw / vh` 方案 |
| :--- | :--- | :--- |
| **驱动机制** | 依赖 JS 计算并修改 `html.style.fontSize` | 浏览器原生 CSS 引擎解析 |
| **首屏性能** | 存在 JS 阻塞、FOUC 闪烁、SSR 水合失败风险 | 无 JS 开销，渲染性能极高，SSR 友好 |
| **应用隔离** | 全局污染（微前端/第三方组件库极易冲突） | 无隔离问题，各自独立计算 |
| **无障碍/字体**| 系统字体放大容易导致整个页面布局崩溃 | 布局与文字可完美解耦 |
| **生态趋势** | 官方库已废弃（如手淘 `lib-flexible`），渐进淘汰 | **W3C 原生标准，当前工业界绝对主流** |

**顶级 H5 专家的 2026 技术选型建议：**
1. **新项目首选：** `vw` + `postcss-px-to-viewport`（工程化自动转换设计稿 `px` 为 `vw`）。
2. **大屏/Pad 兜底：** 结合 CSS `clamp()` 或 `max-width` 限制最大缩放尺寸。
3. **组件级别响应式（未来方向）：** 结合 CSS 容器查询（Container Queries `cqw`），让组件基于“父容器宽度”缩放，而非仅仅基于“浏览器视口宽度”缩放。

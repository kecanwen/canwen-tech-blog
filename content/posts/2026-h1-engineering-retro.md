# 2026 上半年技术复盘：从 AI 编码到 Agent 产品

> 这篇是知识库的「元文章」——不是新增知识，而是把散落的珠子串起来，看看这半年走过的路究竟构成什么图案。

---

## 一、引言

2026 上半年，我的知识库从零膨胀到 **50+ 篇文章、17 个主题**。表面看是一堆独立笔记，但把它们铺开再看，会发现有一条清晰的成长轨迹：

**从一个「用 AI 辅助编码的前端工程师」，逐步成长为「设计 AI 产品和工程体系的技术人」。**

这半年的所有实践，最终都汇聚到同一个命题：**如何让 AI 在 B 端研发中产生可度量、可复现、可信赖的价值。**

本文按三条主线复盘——**AI 协作方法论、Agent 产品设计、工程基础设施**——最后提炼底层相通的思想模式。

---

## 二、主线一：AI 协作方法论 — 从「用得顺」到「系统化」

### 2.1 起源：从痛点出发

年初面对 AI 编码最大的矛盾是：**AI 写得快但写不准**。一次生成 300 行代码，改 bug 花的时间比自己写还多。这个矛盾的根因不是模型能力，而是**信息供给不足**——AI 不知道项目有什么文件、什么规范、什么模式。

### 2.2 八篇实践：逐层深化

这八篇文章不是一次性规划出来的，而是每解决一个问题就记录一篇，逐步长成的体系：

| 篇 | 解决的问题 | 关键产出 |
|----|-----------|---------|
| 一 | AI 不知道项目结构 | spec.md + CLAUDE.md 体系 |
| 二 | AI 对话效率低 | 分步推进、参考答案、约束声明 |
| 三 | 单 Agent 能力有限 | 多 Agent 协作、任务编排 |
| 四 | 测试效率低 | AI 批量生成测试用例 |
| 五 | 编码前想不清需求 | AI 辅助需求分析与方案设计 |
| 六 | AI 引入安全风险 | 脱敏、权限隔离、输出审查 |
| 七 | 团队协作需要统一 | 团队级 CLAUDE.md、AI 审 PR |
| 八 | 完整体系总览 | 决策树 + 能力矩阵 + 速查表 |

### 2.3 核心理念的提炼

整套方法论抽出来三条原则，贯穿所有实践：

1. **信息供给 > 推理能力** — 你在 spec.md、CLAUDE.md、参考答案中提供的上下文，决定 AI 产出的质量上限
2. **降低带宽 > 提高速度** — 花一分钟让 AI 第一次就理解，省十分钟返工
3. **你的判断力 > AI 的执行力** — AI 可以写 10 个文件，但不知道哪些不该写

**→ 往后看**：这三条原则后来直接指导了 BizForge 的产品设计和 Agent 的 prompt 工程。方法论和产品是同一套思维在不同载体上的投影。

## 三、主线二：Agent 产品设计 — 从「工具使用者」到「产品设计者」

### 3.1 转折点：BizForge 的诞生

BizForge 是我从「用 AI 改代码」到「用 AI 做产品」的转折点。它的目标是做一个**引导业务人员产出高质量需求的平台**。

早期的设计停留在「三个角色评审 BRD」——后端、前端、PM。这个设计本质上还是工程师思维：评审一个已经写好的技术方案。

### 3.2 角色重构：认知升级的关键一步

在 角色拆分是否合理的推演 这篇文章中，通过深度推演，完成了关键重构：

```
旧角色（技术视角）         新角色（业务视角）
后端研发负责人     →     业务规划师（值不值得做）
前端研发负责人     →     产品经理（怎么做、口径）
产品经理           →     业务分析师（怎么验收）
```

同时识别出两个致命缺失：
1. **门店/一线运营 Agent** — 医药连锁最核心的落地视角，之前完全被忽略
2. **合规/风控 Agent** — 医药零售监管极严，没有这个角色评审就是纸上谈兵

这次重构的本质是视角切换：**从「技术实现难不难」转向「业务价值对不对」**。

### 3.3 与 AI 方法论的内在联系

回头看，BizForge 的产品设计和 AI Coding 方法论共享同一个底层模式：

| AI Coding 方法论 | BizForge 产品设计 |
|-----------------|-----------------|
| 给 AI 提供结构化上下文（spec.md） | 引导式需求模板，防止空白页 |
| 多 Agent 做方案评审 | 多角色 Agent 做 BRD 评审 |
| 分步推进、拒绝大而全 | 场景模板 → 动态追问 → 评审 → 生成 |
| 显式声明约束 | 每个 Agent 有明确的职责边界和输出物 |
| 参考答案文件 | 历史方案知识库 |

**方法论和产品是同一条思想在不同载体上的投影。**

### 3.4 B 端 Agent 化的深度思考

B 端 Agent 化的难点 是这半年来对 B 端 Agent 化最系统的思考。六层难点拆解：

1. 流程复杂性爆炸 → 显式状态机建模
2. 意图识别困难 → 业务语义层翻译
3. 状态管理与副作用 → Human-in-the-loop 节点
4. 大数据量挑战 → Text-to-SQL + 权限注入层
5. 信任与可控性 → 审计日志 + 回滚机制
6. 工具层设计复杂 → 语义分层 + 动态召回

**核心矛盾**：B 端要求确定性和可追溯，Agent 天性是概率性和黑盒。

**破局方向**：用 Agent 做规划和推理，用确定性代码做实际执行，中间设置清晰的 Human-in-the-loop 节点。这条结论后来也在 只读场景里的职责边界 中做了验证——只读场景最适合 Agent 落地，因为副作用风险几乎归零。

## 四、主线三：工程基础设施 — 从「能用」到「高质量」

### 4.1 三块基石

代码质量、构建工具链、自动化测试——三块基础设施并行推进：

**① TypeScript 类型治理** — [TypeScript any 治理：效果复盘与经验沉淀](/posts/typescript-any-governance)
- 扫描 136 个文件，识别 564 处 `any`
- 按 P0-P4 分 6 轮治理，每轮可验证可回滚
- Services 层 182 处 any 机械替换，32% 问题一次性消除
- 目标是让 `@typescript-eslint/no-explicit-any: error` 成为可能

**② 脚手架全面升级** — 脚手架升级
- Node.js 20→22 LTS（绕开 20 EOL 的死胡同）
- TypeScript 5.5→5.8 + moduleResolution: "Bundler"
- ESLint 8→9 Flat Config + Husky 9→10
- 5 个 Phase 按依赖顺序执行，每阶段独立验证

**③ AI E2E 自动化测试方案** — [中后台 AI 自动化 E2E 技术方案](/posts/schema-driven-b-end-ai-e2e)
- Schema 驱动的六层流水线，AI 只在「数据推断」和「断言翻译」两个窄口发力
- 组件库 data-testid 注入——一次投资、全站受益
- 断言真值来自后端契约，而非 AI 看截图——防「假绿」的命门

### 4.2 共同模式：「AI 作用域最小化」

这三个看似独立的工程实践，实际上共享同一个设计哲学：

> **能用确定性代码做的，绝不交给 AI。**

在 E2E 测试里是「Six-layer pipeline, AI only in layer 3」；在脚手架升级里是「5 个 Phase 按依赖顺序，每阶段独立验证」；在类型治理里是「P0-P4 分级执行，每次运行 type-check」。**确定性 > 智能，可验证 > 高效。**

## 五、横向串联：三个「意料之外的连接」

写这篇复盘前，我本以为这些项目是独立的。但串起来看，发现了三条隐藏的连接线：

### 5.1 文档站 MCP + apifox 路径设计 + BizForge = 「AI 输入预处理」

三个项目目的一致：**为 AI 构建高质量的结构化输入**
- Confluence MCP 把 HTML 转 Markdown，减少 token 浪费
- apifox 路径设计把 300+ 接口按 URI 结构组织成树形目录，提升 Agent 查找效率
- BizForge 的引导式需求模板让业务人员产出结构化 BRD

本质上，这三个项目都在回答同一个问题：**「给 AI 喂什么，AI 才能产出最好的结果？」**

### 5.2 AI E2E 方案 + B 端 Agent 化 = 「作用域最小化」的两面应用

- AI E2E → 把 AI 限制在「测试数据推断」+「断言翻译」两个窄口
- B 端 Agent → 把 Agent 限制在「规划+推理」，执行由确定性代码完成

同一条设计原则，一个用在测试领域，一个用在产品架构领域。

### 5.3 BizForge 角色评审 + AI Coding 多 Agent 协作 = 同源复用

- BizForge 用 4+ 个角色评审 BRD（后端/前端/PM/合规……）
- AI Coding 用多个 Agent 评审方案（架构师/安全/前端/后端……）

设计模式完全一致：**多视角独立评审 → 合并结果 → 人类做决策**。前者是产品功能，后者是开发工作流，但背后的「利用多 Agent 弥补单 Agent 盲区」的思路一模一样。

## 六、成绩与不足

### 成绩
1. **从零构建了一套完整的 AI 协作方法论** — 8 篇系列文章，可被团队复用
2. **完成了从工具使用者到产品设计者的角色跃迁** — BizForge 的角色重构是最有力的证据
3. **在多个领域建立了高质量的技术文档标准** — 每篇都是「可执行的规格说明书」

### 不足
1. **知识沉淀多、回顾提炼少** — 50+ 篇文章缺少跨项目串连，这篇复盘本身就在补这个短板
2. **部分方案停留在纸面** — AI E2E 测试还在 Phase 0，TypeScript 治理的 6 轮中执行了多少需要追踪
3. **广度 > 深度** — 覆盖了 17 个主题，但大多数只有单篇入门，缺少系列化深挖

### 下半年方向
- **系列化深挖** — 选择 2-3 个方向（AI E2E、BizForge 工程化、B 端 Agent 模式）做深度系列
- **落地验证闭环** — 给每个方案文档追加「实际进展」和「效果数据」
- **持续复盘** — 季度一次元文章，把新知识持续串入现有体系
- **增长实验手感** — 把同一套「假设 → 验证 → 度量」用到 AARRR（见 用技术做增长实验），主业不转岗、副业跑通第一笔收款

## 七、写在最后

这半年最大的收获不是学会了某个具体技术，而是建立了 **「实践 → 记录 → 提炼 → 复用」** 的闭环：

```
AI Coding 实践 → 写成 8 篇文章 → 提炼三条原则 → 指导 BizForge 产品设计
                    ↓
            E2E 测试方案 ← 复用「确定性 > 智能」
                    ↓
            B 端 Agent 化 ← 复用「最小作用域」
```

每一次实践都产生了记录，每一次记录都提炼出可迁移的原则。这些原则在不同项目中被复用和验证，形成正反馈。

**技术栈会变、项目会换，但这种「实践—提炼—复用」的模式不会过时。**

# 给 Agent 写规矩：短入口、红线、机器门禁

> 内部分享稿。读完应能回答三件事：Agent 最常在仓库里怎么作死、根目录到底该放什么、本周最小能改哪几份文件。
>
> 和 [spec-first 完整教程](/posts/spec-first-tutorial) 是一对：spec-first 管「进模块先读目录说明书」；本文管「整个仓库的宪法怎么写、怎么守」。人事仓用 spec.md；工作台仓明确不写 spec.md。两套可以并存，底下是同一件事。

---

## 1. 一句话

**别指望 Agent 自己懂这个仓库。门口贴一张短路牌，红线写清楚，能检查的就交给机器。**

Agent 很会写代码，也很会猜。猜错层、帮过头、只改一半、拿过期文档去改对的代码——这四件事比「语法写错」更常见。规矩的目的不是让它写得更文艺，是让它**少猜、少扩 scope、错了能被拦住**。

---

## 2. 先认清：Agent 在仓库里最常干什么蠢事

分享开场可以用这四条对号入座，大家基本都遇到过。

| 作死 | 现场长什么样 | 根因 |
|---|---|---|
| **猜** | 没人写清落哪一端，它按训练数据里的习惯把列表写进 H5 / 新建一套 `features/` | 入口太长或没有「先打开哪」 |
| **帮过头** | 加欢迎语、加样式、把 `localhost` 写进生产配置、顺手升依赖 | 把品味写成了任务 |
| **只改一半** | 两个该对等的示例只改了一个；H5 加了域，小程序没开口 | 没有「必须成对改」的红线 |
| **文档绑架代码** | 旧说明写「禁止往小程序堆业务」，代码已经改成小程序为主体，它把新功能又塞回 H5 | 把过期文档当成法律 |

所以这篇教程不教 Prompt 话术，教**仓库怎么变成 Agent 能遵守的环境**。

人话版判断标准（见 「能读出来的不写，猜不到的必写」）：

> 它自己能从代码里读出来的，不要写；它猜不到的，必须写。

## 3. 和已有实践怎么拼

| 已有 | 管什么 | 本文补什么 |
|---|---|---|
| AI Coding 实践笔记 里的 `CLAUDE.md` | 项目级「怎么干」 | 入口要**薄**，细则按任务分房间，避免一篇 200 行的宪法 |
| [spec-first 完整教程](/posts/spec-first-tutorial) | 目录级 10～30 行说明书 | 有的仓适合 spec.md，有的仓（工作台）用路由表 + 架构脚本代替清单 |
| [用工程化手段约束 Agent 生成代码的质量与一致性](/posts/engineering-constraints-for-agent-code) | 输入约束 → 静态拦截 → 测试自愈 | 把「输入约束」写具体：路牌、红线、用词、地图 vs 标准 |

开源对照来自 **devframe**（Vite DevTools 那一套可移植 devtool 框架）：根目录 `AGENTS.md` 大约 60 行，细则在 `.agents/01`～`09`。他们后来专门把一篇很长的 `AGENTS.md` 拆开，因为 **Agent 会把根文件当整本法律，塞得越长越容易漏、越容易打架**。

我们没有照搬它的 MCP、诊断码、禁止 Zod。搬的是协同方式。落地样本是仓库根目录的 `AGENTS.md`、`.agents/` 和短的 `.cursor/rules`。

## 4. 七条原则（先立，再抄模板）

### 原则 1：门口只贴路牌

根目录 `AGENTS.md` / `CLAUDE.md` 只放：

1. 这是什么仓（认**目录名**，不要认 `package.json` 的 `name`）
2. 处处适用的红线（必须 / 禁止）
3. 「做 X 去读哪一页」的表

细则放到 `.agents/01-定位.md`、`02-用词.md`……或你们已有的 `.cursor/rules/`。Cursor 和 Claude 各放一份**同一内容**的入口：有的工具只读 `CLAUDE.md`，不会去点链接。

目标篇幅：**40～80 行**。超过 120 行，就开始在重复细则了。

### 原则 2：文档是地图，代码和检查才是标准

在入口里写死这一句：

> `.agents/`（或 spec、规则文件）说明现在怎么分层。它和源码打架时，以源码和机器检查为准，**改文档**。

这是整套东西的总开关。默认人性（和默认 Agent）是「规范文件最大，代码去贴文档」。文档一定比测试更容易过期。

### 原则 3：少讲品味，多讲红线

「必须 / 禁止」只标**层边界和落点**，不标缩进和文风。

文风用 ESLint / Prettier；红线写「新页面默认进哪、跨域禁止怎么 import、禁止改哪棵目录」。Agent 对墙遵守得住，对「请写得优雅」会发挥过头。

### 原则 4：同一个东西只准一个名字

给 5～8 个高歧义词做对照表。多仓协作时容易踩坑：

| 要说 | 就是 | 别说成 |
|---|---|---|
| 人事 PC | `hrs-web` | `hrs-api`（那是 Java）、`hrs-h5`（入职登记） |
| 工作台小程序 | `apps/mini-program` | `mp-shell`、薄壳 |
| 工作台内嵌 H5 | `apps/h5` | 现在的 `apps/web`（那是 PC 占位） |
| 结算后台 | `billing-web` | 包名仍可能和目录名不一致 |

名字不统一，Agent 就会改错层。

### 原则 5：能检查的就不靠自觉

纸上的规矩 Agent 会忘。进 lint / 架构脚本 / hook 的规矩，它忘了也过不去。

例外必须**带原因，且能过期**：临时跳过某包的类型检查，补上之后例外还留着，检查应该失败。

### 原则 6：对着样本写，禁止顺手重构

指定 3～6 个「黄金样本」文件。新代码必须长得像它们。任务之外的「顺便规范化」一律禁止。

「像那个一样做」比「做一个漂亮的」有效得多。

### 原则 7：报错要带下一步

给 Agent 看的失败信息，至少三件套：**稳定码或规则名 + 发生了什么 + 该怎么改**。

`throw new Error("出错了")` 和 ESLint 只说 `Unexpected any` 而不指落点，都会把它赶去胡猜。工作台的 `check-architecture.mjs` 每条违规都带 hint，就是这个意思。

## 5. 根文件长什么样（可直接改）

下面是一份「空仓也能套」的骨架。方括号改成你们仓的事实。

```markdown
# [中文名] — Agent 入口

[一句话：什么产品、什么栈]。认目录名 `[文件夹]`，不要用 package.json 的 name。

人类看 README.md。`.agents/` 是地图不是标准：和源码打架时，
以源码和 [pnpm check:architecture / yarn lint] 为准，改文档。

AGENTS.md 与 CLAUDE.md 必须保持同一份内容。

## 处处适用

「必须 / 禁止」标的是层边界和落点，不是个人口味。

- 必须先分端 / 分层再改代码。新能力默认进 [路径]。
- 必须认目录名：[对照一句]。
- 必须对着黄金样本写，禁止以「更规范」重构无关文件。
- 用户没要求不要 commit / push。提交信息根据 git diff 写成 type(scope): 中文描述。
- 禁止 [引入 Umi / 改种子目录 / 在 shared 里引 React / 加本仓没有的 CI] 。

## 层边界

- [3～5 条，抄你们真正会写错的]

## 去哪读

| 任务 | 读 |
|---|---|
| 默认落哪一层 | .agents/01-定位.md |
| 目录怎么叫 | .agents/02-用词.md |
| 命令和门禁 | .agents/03-栈与命令.md |
| 用户一句话落到哪个文件 | .agents/09-意图路由.md |
```

`.agents/` 建议 5～9 页，每页 15～40 行。**不要先造 9 页再开工。** 第一周只要：定位、用词、意图路由、门禁。其它页有痛再补。

Cursor 的 `.cursor/rules/*.mdc` 适合「打开这类文件才注入」（例如只在 `**/page.tsx` 提醒页面禁止 `fetch`）。alwaysApply 的规则保持短硬约束，细节指向 `.agents/`，避免 `AGENTS.md`、`.agents/`、`.mdc` 三处各写一套最后写岔。

## 6. 「去哪读」比长规范更值钱

Agent 的上下文有限。你把一万字塞进根文件，它记不住，还会拿第 3 节和第 8 节互相打架。

好的表长这样（工作台简化版）：

| 用户说法 | 先打开 |
|---|---|
| 首页、工作台 | `apps/mini-program/src/pages/workbench` |
| 订单（已有 H5） | `apps/h5/src/modules/orders/` |
| 接接口 | Schema → `packages/shared`；H5 函数 → 该域 `services/` |
| 环境、域名 | 只 `packages/shared/src/config/env.ts` |
| PC | `apps/web`（空目录，先问） |

人事仓的等价物是 `src/pages/spec.md` 总览 + 各页 spec。形式可以不同，**都必须能回答「先打开哪 1～3 个文件」**。

禁止事项也要写成落点，不要写成口号：

- 「加个筛选」不是新 page
- 「看起来像小程序」默认写小程序，不要再默认塞 H5
- 占位 AppID / 域名保持占位，不编造「官方」值

## 7. 机器门禁：规矩的后半段

输入层再漂亮，没有拦截就等于建议。

仓库里已经有的、建议点名给 Agent 的：

| 手段 | 拦住什么 |
|---|---|
| ESLint 禁 `any` / `as` / H5 的 `../` 跨目录 import | 类型糊弄、错误分层 |
| `check-architecture.mjs`（工作台） | 跨域深入 import、page 里打请求、手写 `useMemo` |
| husky commitlint | `fix bug` 这种无法检索的提交信息 |
| pre-push `pnpm check` | 架构 + 构建没过就推上去 |
| 指定黄金样本 | 「更规范」的顺手重构 |

开源仓还会用 knip（删「看起来没用」的动态依赖）、API 快照（静默改导出）、生成物不入库（并行改同一行压缩 CSS 必冲突）。**按痛点加，不要为了像开源而加。**

没有 GitLab Runner 的仓，写明「禁止加 `.gitlab-ci.yml`」，否则 Agent 会「好心」补流水线。门禁在本地 hook + MR 人工审查，也是一种契约。

## 8. 进阶（做给 Agent 用的产品才需要）

日常写业务页可以先跳过。如果你们在做 MCP、内部工具、把接口暴露给 AI：

1. **内部 API 不等于 Agent API。** 默认关上，显式打开。描述写「什么时候该调」，不要写「返回一个对象」。
2. **界面隐藏 ≠ 不能调。** 权限和「页面上看不看得到」是两回事。
3. **Gateway 只指路。** 工具返回「去读哪份文档 / 现在有哪些实例」，真正干活留给已有代码或模型。不要做成万能遥控器。
4. **给改仓库的人和给用框架的人两本手册。** 维修手册（短契约）和用户说明书（长 skill + 能跑的模板）不要订成一本。
5. **并行任务要有「别再提这事」。** 计划文件记状态；审计时考虑过但决定不做的，写进拒绝清单，避免下一个 Agent 把同一条建议提一遍。

## 9. 本周怎么落地（30 分钟～半天）

### 30 分钟：只做入口

1. 把现有长 `AGENTS.md` 里的红线抄到「处处适用」（不超过 8 条）
2. 「去哪读」先写 6～10 行口令表
3. `CLAUDE.md` 做成和 `AGENTS.md` 同一份
4. 加一句「和代码打架时改文档」

### 半天：拆房间 + 对齐 Cursor 规则

1. 把长文按主题剪进 `.agents/01`～`0n`，每页不超过 40 行
2. alwaysApply 的 `.mdc` 改成短硬约束 + 指向对应页
3. 文件级 `.mdc` 保留（打开 `page.tsx` 才提醒 page 规范）
4. 用一个真实小任务试跑：「加一个入口按钮」

失败信号（和 spec-first 试跑同一套眼睛）：

- 一上来 Glob 全仓
- 把新功能写进错误的端
- 以「更规范」改了任务外文件
- 文档过期时去改代码迁就文档

### 不要一上来做的

- 不要为了对称去全仓生成 spec.md（工作台明确禁止；人事仓才是 spec-first 主场）
- 不要抄开源仓的「禁止 Zod / 必须 MCP / 九篇设计系统」
- 不要把 `.agents/`、`AGENTS.md`、`.mdc` 写成三份不同的法律

## 10. 建议怎么讲（30 分钟）

| 分钟 | 讲什么 | 现场 |
|---|---|---|
| 0～5 | 四种作死 | 让同事报自己踩过的 | 
| 5～12 | 七条原则，重点 1、2、3、5 | 投影工作台现在的短 `AGENTS.md` |
| 12～20 | 对照：拆之前 200+ 行 vs 拆之后 40 行 + 分房间 | 打开 `.agents/09` 口令表 |
| 20～26 | 机器门禁一眼 | 故意在 H5 `page.tsx` 写 `fetch`，跑架构检查看 hint |
| 26～30 | 本周作业 + 问答 | 每个仓先交「8 条红线 + 一张口令表」 |

演示脚本（工作台）：

```bash
# 在 page.tsx 里写一句 fetch('/orders') 后
pnpm check:architecture
# 应看到 hint：将请求移到 modules/<domain>/services/
```

## 11. 反模式

| 看起来很勤快 | 实际效果 |
|---|---|
| 根目录一篇 300 行 AGENTS.md | Agent 前 80 行还在，后面当没看见 |
| 把 Prettier 细则写成必须 | 和 lint 重复，红线被稀释 |
| 文档与代码不一致时改代码 | 旧口径（薄壳 H5）会把架构拉回去 |
| 只写「注意分层」 | 没有落点，等于没写 |
| Cursor 规则、AGENTS、.agents 各写各的 | 一周后三套规矩 |
| 为「AI 友好」加 CI / 加 FSD / 加新状态库 | 帮过头 |

## 12. 收束

回到开头那句：**路牌、红线、机器。**

- 路牌让它找得到房间
- 红线让它不要进错层、不要发挥
- 机器让忘了也过不去

人还是要做判断：这条是层边界还是口味？文档过期了改哪边？例外该不该删？这些判断写进仓库，比写进某一次对话更值钱。

## 延伸问题

- 人事仓的 spec.md 和工作台的「禁止 spec.md + 架构脚本」，怎样在工作区总索引里写清「哪个仓用哪套」，避免 Agent 串台？
- 口令表腐烂的信号是什么？要不要用一次失败的落层任务反向加一行？
- 提交信息强制由 Agent 根据 diff 生成之后，MR 标题要不要同一套词表，方便以后 `git log -S`？

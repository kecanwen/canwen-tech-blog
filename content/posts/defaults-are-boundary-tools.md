# 默认值、可选链和 try-catch 是边界工具，不是不确定时的退路

周二下午，测试说订单页有时候是空的。

你打开页面，确实空。查接口，200，返回 `[]`。你说后端没数据。测试说：同一个账号，换个页面就有订单。

你从页面往回查：组件收到 `[]` → 请求参数里 `userId` 是空串 → 那个必填参数根本没传进来 → 它在函数入口被 `= {}` 接住了。

一个必填参数漏传，一路走到页面上，变成了「这个用户没有订单」。这条路上没有任何一处报错。

---

**三种完全不同的情况——调用方没传、接口本来就没有、请求失败了——在页面上是同一种安静。** 它们看起来都像正常结果：状态码 200，页面照常渲染，日志干净。我把它叫「空成功」：看起来成功了，其实什么都没成功。

下面讲的是空成功怎么被造出来，以及怎么在它诞生之前把它拦掉。

---

## 一、被抹掉的是「这是哪一种情况」

前端排障，贵的不是找到哪一行代码，而是**认出这是哪一种事实**。三种事实的处理方式完全不同：

| 事实 | 该停在哪 | 用户该看到什么 |
|---|---|---|
| 调用方没传必填项 | 类型或调用点，请求不发出 | 开发期就红，不进页面 |
| 协议允许缺失，响应里确实没有 | 拿到响应的那一层 | 空态，或按缺省分支渲染 |
| 请求失败（网络、权限、业务码） | 页面的错误态 | 原因和重试 |

默认值、可选链、吞掉异常的 `catch`，做的是同一件事：**把这三行合成一行**。合成之后，下游只看得见「没有数据」。而没有数据既像成功，也像失败，日志里往往连一条报错都没有。

这不是语法问题。`= {}`、`?.`、`catch` 各自都有正当用途。问题出在它们被用来**推迟一个本该当场做的决定**：这个值，按契约，存在还是可以缺。

## 二、默认值：把「没传」说成「传了空的」

**它像什么**：给参数一个兜底，别因为少传一个参数就把函数搞崩。

```ts
function listOrders(params: { userId?: string; status?: string } = {}) {
  return request.get('/orders', { params });
}

listOrders();
listOrders({ userId: '' });
```

**它偷走了什么**：函数内部看不出这两次调用的差别。签名上 `userId` 还在，运行时它可有可无。必填漏传时，请求带着空查询发出去，接口返回空数组，页面写成「暂无订单」。缺陷停在调用方，症状出现在接口结果里——中间隔了几个文件，没人会往调用点想。

**判据**：默认值合法的地方只有一处——契约规定「不传」和「传空」是同一语义，而且空值不会被下游当成「查全部」或「查成功」。分页的 `page = 1` 通常属于这种，因为协议写了默认页码。查询对象整体默认成 `{}` 很少属于这种，它只是让调用点少写一个参数。

必填就不要给默认值，让类型强制传入：

```ts
function listOrders(params: { userId: string; status?: string }) {
  return request.get('/orders', { params });
}
```

漏传 `userId` 在编译期结束。**可空的是 `status`，不是整包参数**——这一句话就是全部区别。

还有一个更安静的变体：`params.userId ?? ''`、`params.userId || currentUser`。空字符串，以及「替用户补一个当前人」，都会把「没传」变成一次真实请求。补数据如果是产品规则，就写进一个命名清楚的函数，例如 `resolveActor(session)`，并且在没有会话时进入未登录；不要在图省事的请求函数里顺手补上。

## 三、可选链：缺数据不再有一个能打断的点

**它像什么**：这个字段可能没有，用 `?.` 安全地读一下，别白屏。

```ts
const city = profile.address?.city;
```

这是它的正当用法：`address` 可空写在契约里。用 `?.` 是在承认这个事实，但后面必须有分支——没有城市时展示什么。

**它偷走了什么**：

```ts
const name = order?.buyer?.name ?? '';
```

如果订单详情接口保证返回 `buyer`，这条链就是在为「我不确定后端会不会漏字段」买保险。链子可以在任意一层断开，后面的代码只能继续对着空字符串渲染。页面是空白，控制台没有报错，因为异常早在 `?.` 那一层就被消掉了——**缺数据不再有一个可以打断的点，栈也指不回第一次拿到残缺响应的地方**。

**判据**：从类型上就能看出来。`order?.buyer?.name` 的结果是 `string | undefined`，下游每个使用点都得再防一次；不确定性从边界扩散进了整棵组件树。协议保证存在的对象，在边界上收一次，里面就都是确定的 `string`：

```ts
if (!order.buyer) {
  return <ErrorState message="订单缺少买家信息" />;
}

return <BuyerName name={order.buyer.name} />;
```

这一层把「协议被打破」当成失败，而不是当成一个空名字。真正可空的字段，留在这层用普通判断处理，不必让整棵树都变成可选。

## 四、`try/catch`：失败从调用栈里消失

**它像什么**：网络抖动很常见，别让一个异常把整个页面搞崩。

```ts
async function listOrders(userId: string) {
  try {
    return await request.get<Order[]>('/orders', { params: { userId } });
  } catch {
    return [];
  }
}
```

**它偷走了什么**：网络断开、401、业务码「无权限」、自己把字段名写错，到了页面都是 `[]`。空态组件正常出现，重试没有入口，因为已经没有错误了。监控如果只看「接口返回后的渲染」，还会把这次失败统计成一次成功的空列表——**第一次失败被写成了 200，之后就再也没人知道它失败过**。

请求失败是页面状态的一种，不是 service 要抹平的噪声。**`catch` 写得越靠内，能处理这次失败的人越少**：service 吞掉之后页面失去错误态，页面再吞掉之后用户只剩一块空白。

**判据**：合法的 `catch` 只有两种。

1. 在页面（或这一屏的数据钩子）里接住，写入错误态，展示消息，提供重试。
2. 把一种**已经命名的结果**翻译成控制流，例如用户取消扫码。这种分支要判断具体错误，然后结束，不要落到一个返回空数据的默认分支。

```ts
try {
  const orders = await listOrders(userId);
  setOrders(orders);
  setStatus(orders.length === 0 ? 'empty' : 'ready');
} catch (caught) {
  setMessage(caught instanceof RequestError ? caught.message : '加载失败');
  setStatus('error');
}
```

空列表和失败是两种状态：前者是请求成功且结果为零，后者是请求没有成功。混成一种之后，产品和研发会对着同一块空白争论「到底有没有数据」。

宽泛的 `catch (e) {}` 还有第二个问题：**它接住的比你想接的多**。渲染期抛出的类型错误、拼错的函数名，都会被同一个空 `catch` 吃掉。要接的是请求错误，就判断错误类型；判断不了就别接。

## 五、三层会接力

这三种写法很少单独出现。真实的链路长这样：

1. 调用点用 `= {}`，必填条件没传也发得出请求。
2. service 用 `catch` 返回 `[]`，失败变成空成功。
3. 页面用 `list?.map(...)` 和 `item?.name ?? '-'`，残缺字段变成占位符。

**每一层都觉得自己在防御。合在一起，没有任何一层保留「这次为什么没有数据」。** 日志里是 200 加一个空数组，复现步骤只剩「打开页面，什么都没有」。

到这里，它已经不是个人编码习惯的问题了。一个空值从入口漏到渲染层，中途穿过几个文件都没有被拦一次，说明这个系统**不区分「没有」和「失败」**——这是结构问题，只是它的症状长得像页面空白。

修的时候不要从页面的 `?.` 开始删。先问契约：这个字段必填还是可空？失败允许被谁看见？然后从内往外拆：

- service 只发请求、只返回契约里的类型，不补默认查询，不把异常换成空集合。
- 调用方保证必填参数来自已经成立的状态（已登录的用户、路由上的 id）。没有这个状态，就不要调用。
- 页面在拿到响应时分成加载、有数据、空、失败四种。只有「协议允许缺失」的字段，才在渲染前做缺省分支。

## 六、同一条代码，四个高度

`order?.buyer?.name` 这一行，站在四个高度上是四个不同的问题：

| 高度 | 会问的问题 | 对应的做法 |
|---|---|---|
| 语法 | 报错了吗 | 加个 `?.` |
| 类型 | 缺字段有没有编译错误 | 必填、可空写进签名 |
| 契约 | 后端本来就该返回它吗 | 边界校验，残缺就是错误 |
| 架构 | 失败和空数据分得开吗，监控看得出来吗 | 失败是状态，不是数据 |

只站在第一层，你会给出一串禁令，然后被「分页默认页码」「地址可以为空」这类正确反例推翻。站到第四层，问题会变成另一个：**这个系统还知不知道真相？** 一个把失败渲染成空列表的系统，不是不健壮，是看不见自己出了什么事。

两种写法都能通过测试，差别只在出事那天谁先找到原因。加 `?.` 的那版，你只能从一块空白往回猜；分层的那版，第一次拿到残缺响应时它就已经告诉你了。

## 七、契约写在类型上，不写在调用点的补丁上

一个值是否可选，由接口契约决定。**类型是契约在前端的投影，不是调用时的缓冲垫。**

- 必填参数和必填字段写成必需属性。漏传、漏返回，让编译或者边界校验失败。
- 可空字段写成 `field?: T` 或 `T | null`，并在拿到它的那个函数里分支。分支之后传给子组件的是确定类型。
- 请求函数的返回类型不要包含「失败时的空值」。失败用抛出或 `Result`，让调用方没办法把它当数据用。

`Result` 并不比异常更高尚。关键是**失败不能伪装成数据**。返回 `{ ok: false, message }` 和抛 `RequestError` 都可以，只要页面必须处理失败那一支，不能靠默认空数组蒙混过去。

响应边界如果要防后端漏字段，防一次就够。在请求出口用校验把残缺响应变成错误，而不是让每个组件各自 `?.`。校验失败和业务空数据不是一回事，文案也该不同：「接口数据不完整」和「没有订单」，对排查的意义完全不同。

## 八、评审时怎么说

不要把这三样语法收成禁令。中级工程师马上能举出反例：分页默认页码、地址可空、页面必须接住网络错误。**禁令会被一个正确的反例推翻，然后整条原则被一起丢掉。**

可以这样说：

> 默认值、可选链、`try/catch` 都是边界工具，不是不确定时的退路。一个值是否可选，由接口契约决定，不由我们在调用点临时补一个空对象决定。必填就让类型强制传入；协议允许缺失，就在拿到响应当下分支处理；请求失败就让错误留到页面的错误态。不要在 service 里把没传、没有、失败都收成一份空数据。空数据看起来像正常结果，排查时只能倒着猜是哪一种。

先把允许写的情况说清，再给规则，对方才听得进去：

1. 查询条件本身可选；
2. 接口文档写明这个字段可空；
3. 页面边界需要把失败展示给用户。

这三种是在处理**已知事实**。为了「免得报错」而加的，是在隐藏**还没决定的契约**。

判断只需要三问：

1. 这个值按契约存在吗？
2. 它缺失代表哪一种事实？
3. 这个事实该被谁看见？

三问都能答清楚的，怎么写都不会错。答不清楚的，说明契约没定——先去定契约，别在调用点补一个空值。

---

回到那个周二下午。

那次空白的真正成本，不是那个没传的 `userId`，而是**它走到页面上之前，三种事实已经被合成了一种**。参数漏传、接口没有、请求失败，在界面上长得一模一样，所以你只能倒着猜。

让必填的地方编译不过，让可空的地方在边界分支，让失败留在页面的错误态。这些做法的共同点只有一个：**别让不同的原因，长得一样。**

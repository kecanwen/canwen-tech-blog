# 自动化测试全景：分层、策略与取舍

> [!IMPORTANT]
> **本文探讨的核心问题：**
> 1. 自动化测试的各层（单元/集成/E2E）之间到底是什么关系——成本、速度、可靠性如何权衡？
> 2. B 端中后台页面的测试分层策略与 C 端有什么本质不同？
> 3. "测试覆盖率"这个指标容易误导什么？真正的测试有效性从哪来？

---

## 一、测试金字塔：一个被反复验证的模型

Mike Cohn 在 2009 年提出的测试金字塔，至今仍然是讨论测试策略的起点。它的核心洞察是一个**经验事实**：

> 越底层的测试，编写越慢但执行越快、越稳定；越高层的测试，编写越快但执行越慢、越脆弱。

```
         /\
        /  \        E2E 测试（慢、贵、脆）
       /    \
      /------\      集成测试（适中）
     /        \
    /----------\    单元测试（快、便宜、稳）
   /            \
```

三层各自的特征：

| 维度 | 单元测试 | 集成测试 | E2E 测试 |
|------|---------|---------|---------|
| 执行速度 | 毫秒级 | 秒级 | 秒～分级 |
| 定位精度 | 精确到函数 | 精确到模块间交互 | 精确到用户操作路径 |
| 失败排查成本 | 低（定位到行） | 中 | 高（可能是任何环节） |
| 环境依赖 | 无（纯内存） | 少（部分依赖） | 多（浏览器、后端、网络） |
| 编写速度 | 慢（逐函数写） | 中 | 快（录制/自然语言） |
| 重构抗性 | 高（测逻辑而非实现） | 中高 | 低（测 UI 结构） |

测试金字塔背后的工程原则是：**用大量快速稳定的底层测试覆盖逻辑，用少量高层测试验证真实用户路径。** 比例建议通常是 70/20/10（单元/集成/E2E），但这个比例不是教条——它取决于你的业务形态。

## 二、B 端页面的测试分层特点

B 端（中后台）页面的测试分层与 C 端有**结构性差异**，直接套用通用金字塔会踩坑。

### 2.1 B 端的"三层"重心偏移

通用金字塔把单元测试作为主力，但在 B 端业务中：

- **单元测试的边际价值递减很快**：B 端前端的核心复杂度不在纯函数逻辑，而在**配置驱动的组件编排**和**异步数据流**。一个筛选区 + 表格页面的"逻辑"主要来自字段配置和 API 响应，纯函数逻辑很少。
- **E2E 测试的 ROI 反而很高**：因为 B 端的交互模式高度固定（筛选区 → 查询 → 表格渲染 → 弹窗编辑 → 保存），一个 E2E 用例可以覆盖一整套页面配置的完整链路。

这是我的实际观察：

| 测试类型 | C 端（电商/H5） | B 端（中后台） |
|---------|---------------|--------------|
| 核心复杂度 | 渲染性能、动画、手势、跨端适配 | 字段规则联动、数据流、权限组合 |
| 单元测试价值 | 高（交互逻辑多、状态复杂） | **中低**（纯函数少，配置串联多） |
| 集成测试价值 | 中（API 调用有限） | **高**（页面=配置×接口的组合游戏） |
| E2E 测试价值 | 中低（页面变化快、结构不稳定） | **高**（交互模式固定、复用性强） |

**结论：B 端的测试金字塔应该更扁平——E2E 和集成的比重远高于通用建议。** 这不是理论上更优，而是投入产出比的实际选择。

### 2.2 B 端的"分层"更多维度

B 端的测试分层不能只按金字塔的三层来切。在 [中后台 AI 自动化 E2E 技术方案](/posts/schema-driven-b-end-ai-e2e) 中定义了一个更精细的六层流水线。从概念层面，B 端测试应该从这三个维度同时分层：

**维度一：按测试范围（纵向）**
- 组件级（单个 `data-testid` 定位的元素是否能渲染交互）
- 页面级（单页面的筛选+表格+弹窗流）
- 跨页面级（多步骤业务流程，如"创建门店→分配标签→验证生效"）

**维度二：按断言真值来源（横向）**
- **后端契约断言**：拦截 API 响应，断言返回数据的结构和值（最可信）
- **DOM 结构化断言**：元素存在、行数变化、特定文本出现（中等可信）
- **视觉断言**：截图比对、AI 判断布局正确性（兜底）

**维度三：按维护层级**
- **确定性层**（`data-testid` + 组件库 DSL）：不受 UI 改版影响
- **配置层**（JSON Schema / PageContract）：字段增减时更新
- **AI 推断层**（测试数据生成）：自动适配，但需要校验门禁

这三层维度互相正交，一个测试用例可能同时属于"页面级 × 后端契约断言 × 确定性层"。设计测试框架时，应该在三个维度上都有明确策略，而不是只考虑"测什么"。

## 三、覆盖率的陷阱

### 3.1 行覆盖率 ≠ 测试有效性

一个常见的误区：追求 90% 行覆盖率。问题是：

- **行覆盖率只告诉你"代码被执行了"，不告诉你有断言验证了结果。** 一个没有断言的测试可以跑出 100% 覆盖率但零价值。
- **覆盖率数字可以被"测了但不痛不痒的用例"轻松刷高。** 表单能渲染、按钮能点击、页面不报错——这些用例跑绿了，核心业务流程却可能一笔没碰。

这就是 团队自动化测试的现状 中提到的**虚假覆盖**问题。

### 3.2 有效性来自断言质量

测试的有效性公式不是 `覆盖率 × 用例数`，而是：

```
测试有效性 ≈ 断言真值的可靠性 × 断言覆盖的边界数量
```

- **断言真值的可靠性**：后端响应数据 > DOM 结构化属性 > 视觉/LLM 判断
- **断言覆盖的边界数量**：合法值、非法值、边界值、空值、重复值——每个字段的每条规则都会对应一个用例

[中后台 AI 自动化 E2E 技术方案](/posts/schema-driven-b-end-ai-e2e) 中提出的"禁止空断言"铁律，正是对这个公式的工程化落实：只测到了算是没用的，测到了对的东西才有用。

## 四、一个务实的取舍框架

做自动化测试绕不开一个根本问题：**投入多少、期望什么回报**。以下是我判断取舍的框架：

### 4.1 三层过滤

决定要不要为一类场景写自动化测试，过三关：

1. **频率关**：这个操作/流程，改代码后会不会反复验证？不会→不值得自动化
2. **确定性关**：期望的结果是否能精确描述？不能→自动化了也检不出真正的错
3. **成本关**：自动化的维护成本 < 手工执行的累积成本？否→不如手点

### 4.2 B 端甜区速查

| 场景 | 频率 | 确定性 | 成本判断 | 结论 |
|------|------|--------|---------|------|
| 筛选+表格查询 | 极高 | 高（API 响应可断言） | 模板化后极低 | ✅ 最甜 |
| 新增/编辑弹窗 | 高 | 高（创建/更新接口可断言） | 模板化后低 | ✅ 甜 |
| 表单校验边界 | 中（字段规则变更时） | 高（Zod rules 明确） | 可自动派生 | ✅ 甜 |
| 跨页业务流程 | 低（需求稳定后很少变） | 高 | 中 | ⚠️ 看情况 |
| 页面视觉布局 | 中（重构/换肤时） | 低（什么算"好看"模糊） | 高（截图diff人工审） | ❌ 不值 |
| 第三方集成 | 低 | 中（依赖外部状态） | 高（Mock 成本） | ❌ 不值 |

### 4.3 不同规模团队的不同策略

这个取舍不是一成不变的，它会随着团队规模和业务阶段变化：

| 阶段 | 策略 | 理由 |
|------|------|------|
| 0-5 人创业团队 | 只做最核心 2-3 个 E2E 场景 | 快速交付比测试重要 |
| 10-30 人业务团队 | E2E 覆盖主干流程 + 集成测试补核心逻辑 | 提测质量是瓶颈 |
| 50+ 人成熟团队 | 三层全铺 + Schema 驱动批量生成 + CI 门禁 | 回归护城河必须 |
| 多团队中大型系统 | 分层自动化和 AI 辅助生成并行 | 跨团队协作的契约保障 |

## 五、总结

- **测试金字塔的核心洞察是分层权衡，但 B 端需要更扁平的比重：E2E 和集成的 ROI 远高于通用建议。**
- **测试有效性不来自覆盖率数字，来自断言真值的可靠性和边界覆盖的广度。**
- **B 端测试应该从"范围/断言源/维护层级"三个维度同时分层，而不是只用金字塔一个模型。**
- **投入自动化的决策框架：频率 × 确定性 × 成本。**

延伸问题：
- PageContract 提取器能否自动估算每个页面层的"预期 ROI"？
- 同一个系统里，不同模块的测试成熟度不同，能否做"分层自愈"——低成熟度模块走 AI 兜底，高成熟度走确定性断言？
- 测试金字塔在 AI-native 技术栈（代码大多由 LLM 生成）下是否还成立？如果代码质量方差变大，测试策略应该如何响应？
